# Portable bundles, recovery, and Windows

`study export DIR --out FILE.zip --kind task` packages reviewed inputs and task state; `--kind results` also includes available result evidence. Treat either archive as potentially private engineering data. Export rejects active locks, unfinished runs, and owned live processes. `study import FILE.zip --out NEW_DIR` validates archive paths, member types, hashes, required files, schema, study identity, and fingerprints before installing to a new destination. Use `--expected-study-id` when the receiving workflow already has an expected identity.

The manifest's `study_fingerprint` identifies canonical study/base inputs. `code_fingerprint` binds the study to the compiler/study implementation that prepared it. The code hash normalizes CRLF to LF, so Windows line endings alone do not change it. Match that fingerprint at the receiving host; do not copy result files into a different study or bypass identity checks. A mismatch calls for a fresh plan or the matching code, not manual manifest edits.

On Windows, use Python 3.13 and install the `[study]` extra for build123d and numerical/model dependencies. The base CLI can be installed without NumPy; study model operations need the study extra. Real Mechanical execution additionally needs the compatible ANSYS clients, licensed local installation, and an explicit `--execute`. The repository's `tools/run_study_windows.ps1` accepts an imported study directory, checks that the installed `code_fingerprint` matches, and runs with `--resume --json`; `-Execute` forwards the explicit execution switch. It does not install dependencies, change execution policy, or select a different code version.

After an interruption, `study recover DIR` checks the local lock owner and recorded owned Mechanical processes. It refuses recovery if it cannot prove the local processes have stopped. Successful recovery removes the stale lock and marks abandoned `RUNNING` attempts `INTERRUPTED`, preserving their records so a later execution creates a new attempt. It cannot establish process state on another host. Inspect the status and ledger, then resume the same authorized batch with the same code and environment. Never delete an RST, attempt folder, lock, or manifest entry to simulate success.

The reported `build123d` 0.11.1 font issue and the historical 0.9.1 path are prior observations. Neither demonstrates current Windows compatibility. Record Python, build123d, platform, CAD generation outcome, and the actual Mechanical environment in any new acceptance evidence. Keep unverified CAD/font behavior `NOT_RUN`.
